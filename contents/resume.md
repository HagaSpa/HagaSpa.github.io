#### プロジェクト 1: Platform の属人化解消とコスト最適化

- 期間: 2025/08〜現在
- 役割: Platform Engineer として設計・実装を担当し、nginx-ingress から Gateway API への移行を主導
- 規模: 複数プロダクト（クラウドファクタリングの OLTA、請求書サービスの INVOY ほか）の GKE クラスタと CI/CD
- 技術: GKE, Kubernetes（HPA / VPA）, Gateway API, Terraform, GitHub Actions, Cloud Monitoring
- 課題: Platform（インフラ・デプロイ・監視）の運用が実質 1 人に依存しており、障害対応もコストの判断もその 1 人に集中していた。開発環境もマルチゾーン構成で動いており、必要以上のコストがかかっていた。ingress には EOL を迎える nginx-ingress を使い続けていた
- 取り組み:
    - 全開発環境の GKE クラスタをシングルゾーン構成へ移行。新クラスタの構築から DNS の切り替えまでを担当した
    - 負荷試験で Resource Request を適正化し、HPA の上限に達したときの最大処理能力を明らかにした。VPA の推奨値も本番に反映した
    - INVOY の CPU 高騰障害で、高負荷の Pod が特定ノードに偏る原因を特定し、livenessProbe の設定不備による無限ループも見つけて修正した
    - 1 つのリポジトリが GitHub Actions の実行時間の 42% を占め、そのうち約 7 割が E2E テスト（Playwright）であることを特定し、E2E を main へのマージ時だけ実行するようにした
    - nginx-ingress から Gateway API への移行に向けて ADR を書き、annotation の互換性、LB 経由でのヘッダー変化によるアプリケーションへの影響、Gateway + IAP による Service 単位の認証を検証した。移行手順書と計画も作り、プロダクトチームに引き渡した
    - 他のエンジニアが GKE の構築などを実際に手を動かして学ぶ場「Platform Contributors」を始めた
- 成果:
    - 開発環境のシングルゾーン化で GKE のサーバ費用を約 43% 削減
    - GitHub Actions の実行時間を月約 14,700 分削減（当該リポジトリの約 9 割、Org 全体の約 1/4）
    - Gateway API への移行や GKE の構築を、プロダクトチームが自分たちで進められる体制にした。この取り組みはテックブログで公開し、全社員が集まる会でも開発組織の代表として AI 活用をテーマにした LT に登壇した
    - テックブログ: https://techblog.olta.co.jp/entry/2026/07/22/071625

#### プロジェクト 2: 全社ガバナンスとセキュリティ

- 期間: 2026/05〜現在
- 役割: 方針の決定から実装、全社への周知までを担当
- 規模: GitHub Org（約 130 リポジトリ）、Terraform Cloud、Jenkins など、全社共通の開発基盤

- 取り組み:
    - GitHub Org と Terraform Cloud の管理、Jenkins の認証を CTO 室で引き継いだ。Jenkins の GitHub 認証は、より権限の狭いトークンに切り替えた
    - GitHub の Teams を雇用・契約形態（正社員・業務委託）に基づいて再設計し、リポジトリ作成・fork の権限を管理者に限定した。権限付与を Terraform の PR 経由で行う運用に切り替え、全社に告知した
    - 社内リポジトリに残っていた本番環境の認証情報を発見し、インシデント対応を主導した。証跡を保全し、監査ログから不正利用がないことを確認したうえでキーをローテーションした
    - 再発防止として、全リポジトリへの Secret Scanning の導入、アクセスログの永続化、全プロダクトの認証経路の棚卸しを行った
    - 他社のサプライチェーン攻撃事例を受け、個人アクセストークンを削除して GitHub Apps に移行した。開発ツールをどこまで統制するかを Low / Mid / High の 3 段階に整理し、判断材料としてまとめた
- 成果:
    - GitHub の権限変更が PR として残り、誰がいつ何を変えたかを追える状態になった
    - インシデントは不正利用がないことを確認して収束させた。同じ種類の漏洩は全リポジトリで検知できるようになった
    - 2026 年度下期は、Ruleset / branch protection の Terraform 管理への移行と、未使用リポジトリの整理を進めている

#### プロジェクト 3: データ基盤の信頼性向上

- 期間: 2025/08〜現在
- 役割: Data Engineer として、dbt・Looker の設計・実装と運用を担当
- 規模: BigQuery 上のデータ基盤（dbt / Looker / Airbyte）。ビジネス部門を含む全社が利用
- 技術: BigQuery, dbt, Looker（LookML）, Airbyte, GitHub Actions, Salesforce
- 課題: dbt の変更はローカルで確認するしかなく、後続モデルの実行漏れなどの不具合がマージ後に見つかっていた。マスタの手動管理やハードコードも残っていた。データの登録漏れや更新の停止にも気づけない状態だった
- 取り組み:
    - 提携金融機関に支払う収益分配（レベニューシェア）の計算方法を見直すプロジェクトで、データ仕様書の作成から dbt・Looker の model / explore の追加まで一貫して担当した
    - dbt では PR ごとに BigQuery のデータセットを自動で作る CI（GitHub Actions）と、manifest を使った差分ビルドを実装した。Looker にも LookML の CI を導入した
    - ユーザーを経由元の提携金融機関ごとに分ける区分はハードコードされていたため、dbt の seed（マスタ）で管理する形に移し、翌朝の自動チェックで登録漏れに気づけるようにした
    - INVOY の分析用データ（77 テーブル）の更新が約 4.5 か月止まっていたため、原因を特定して復旧し、影響を受けた集計も補正した
    - GA4 のイベントログのモデルを incremental 化し、Partition Pruning が効く形にした
    - Salesforce から BigQuery へ同期する Airbyte のコネクタをバージョンアップし、データ検証のアラートを整えた
- 成果:
    - 2026/05 に新しい計算方法での本番運用を始めた。提携金融機関向けのデータ抽出は保存済み Look にして、非エンジニアの担当者が自分で CSV を出せるようにした
    - PR の時点で変更後のデータを確認できるようになり、ローカルでの動作確認が不要になった
    - 手動の CSV 運用を廃止し、登録漏れを自動で検知できるようにした
    - GA4 のスキャン量を 72.9GiB から 25.5MiB に削減（99.97% 減）
    - テックブログ: https://techblog.olta.co.jp/entry/2026/06/29/161346
